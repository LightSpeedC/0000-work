## クラウドの会話ログ（2026-10-14）

1 件 / 未 1 / 着手 0 / 済 0

### `i261014-01` クラウドのセッションでは会話ログが etc/history に残らない ⬜ **未**

共通ルール「記録と運用」の「セッションログの自動保存」は、会話ログ（JSONL）を各プロジェクトの `etc/history/jsonl/` に写す。仕組みはホームの `~/.claude/settings.json` のフックで、クラウドの環境にはホームの設定が無いため動かない。

会話ログ自体はコンテナの中にある（ホームの `.claude/projects/` の下。このセッションで約 5.4 MB）。ただし `etc/` は git の管理外で、写してもコンテナが作り直されると一緒に消える。**コンテナの外へ持ち出す手段が要る。**

### 案

| 案 | やり方 | 良い点 | 気になる点 |
|---|---|---|---|
| A. Windows に引き継ぐ | 作業後に Windows PC で `claude --teleport` し、セッションを手元に持ってくる。手元のフックが `etc/history/` に写す | 仕組みを足さない。ログが外に出ない | 毎回手で引き継ぐ。引き継いだ後に手元の写しが走るかは未確認 |
| B. 非公開リポジトリに push | セッションの終わりにフックで JSONL を非公開リポジトリへ push し、Windows 側で pull する | 自動で残る | 会話の全内容が入るので必ず非公開。容量が積み上がる。リポジトリの作成はユーザ側の操作 |
| C. 都度受け取る | 区切りでログを SendUserFile で受け取るか、Google Drive に置く | すぐできる | 手作業。取り忘れると消える |

**やること**

- ⬜ **未** 案を決める（ログを外に出さない A から試すのを提案している）
- ⬜ **未** A なら、このセッションを Windows に引き継ぎ、`etc/history/jsonl/` に写るかを確かめる
- ⬜ **未** 決まった手順を共通ルール「クラウド作業のルール」に書く

## クラウドの Obsidian Vault（2026-10-14）

1 件 / 未 1 / 着手 0 / 済 0

### `i261014-02` クラウドのセッションで Obsidian Vault を毎回使える形にする ⬜ **未**

2026-10-14 に、このセッションへ `LightSpeedC/ObsidianVault`（非公開）を書き込みもできる形で追加し、プロジェクトの隣の `ObsidianVault/` に clone した。**このセッションだけで使える状態**で、新しいセッションには引き継がれない。

- **取得**: 非公開なので、セッションに Vault を追加していないと clone できない。`cloud-session-start` は Vault を取らない
- **メモリの読み込み**: Windows ではセッション開始時のフックが `memory/!memory.md` を読み込ませている（共通ルール「Obsidianメモリ連携ルール」）。クラウドにはこのフックが無い
- **置き場**: 追加したときの既定の clone 先は小文字の `obsidianvault` で、隣に置いた `ObsidianVault/` はセッションへの登録を拒否された。Vault に `CLAUDE.md` は無いので実害は無い。大小だけが違う名前を作らないため、`ObsidianVault/` のままにする
- **書き戻し**: メモリを更新したら commit・push が要る。`0000-work` の Stop フックの扱いは Vault には及ばないので、共通ルールどおり明示を待つ

**直し方の案**（提案中）: `cloud-session-start` に、Vault が追加されていれば clone し、無ければ何もしない処理と、`memory/!memory.md` を出力に載せる処理を足す。変更先は `ai-agent-tools` と共通ルール「クラウド作業のルール」。

**やること**

- ⬜ **未** 取得とメモリの読み込みを、自動にするか手動にするか決める
- ⬜ **未** 自動なら `cloud-session-start` に足し、Vault を追加したセッションと、していないセッションの両方で確かめる
- ⬜ **未** 決まった扱いを共通ルール「クラウド作業のルール」に書く
